# 社媒热度分析工作流：实施方案

- 日期：2026-10-10
- 状态：方案阶段；小红书文件驱动采集 CLI 已实现，按要求暂未测试
- 项目目录：仓库根目录，文档不记录本机绝对路径
- 目标平台：小红书、抖音

## 1. 目标与成功标准

构建一个可移植的单用户应用，让用户能在 Web UI 中维护关键词和对标账号，配置平台筛选与运行频率；手动、定时或通过 Agent 触发采集；保存内容和互动数据的时间快照；生成带作品链接和数据证据的分析报告。

首版验收标准：

1. 首次启动能运行环境预检，清楚报告 OpenCLI 版本、命令能力、浏览器桥接、账号登录和 LLM 配置状态。
2. Web UI 可以新建/编辑/暂停监控配置，分别为小红书和抖音设置关键词、账号、筛选项、单次上限和时间范围；筛选可组合，并有明确的重置入口。
3. 一次运行可产生有开始/结束时间、状态、采集数、失败原因的运行记录；采集成功项能保存正文/描述、标签、作者、链接、发布时间及平台提供的互动指标。
4. 多次运行按“平台 + 作品 ID”去重，但保留每次指标快照，用于比较变化；缺失字段保留为 null/未知。
5. 报告包含概览、候选作品排行、标签/主题聚类、代表性内容、互动表现和可执行观察；每条结论可回溯到作品 ID/链接及对应快照。
6. Web UI、MCP 工具和定时任务走同一套核心服务和数据库，避免出现三套不一致的执行逻辑。
7. 配置可导入/导出；密钥、Cookie、浏览器登录态不进入导出文件或 Git。

## 2. 边界与产品原则

### 首版做

- 关键词搜索：每个监控配置可指定平台、关键词、筛选条件及每词采集上限。
- 对标账号：维护账号主页 URL/平台账号标识，采集可访问的近期作品。
- 内容详情：尽量补齐正文/描述、标签、作者、发布时间、作品 URL 和平台可见的互动指标。
- 筛选操作：UI、CLI 与 MCP 支持按平台一次设置一个或多个筛选项；同一选项组单选、不同组可组合；提供显式“重置筛选”将该平台的全部筛选组恢复默认。应用后检查当前选中项和结果刷新，不能把未生效的筛选当成功。
- 历史快照：保存点赞、收藏、评论、分享、播放等指标及采集时间，支持新旧快照对比。
- LLM 报告：总结共同主题、内容切入点、互动特点、差异和后续选题线索。
- 调度：UI 创建、查看、暂停、恢复和删除周期任务；每个任务有时区、并发/重叠策略和失败状态。
- Agent 接入：MCP 工具用于查看配置、触发运行、查询运行状态/报告和管理计划任务；附一个精简 Codex Skill 作为自然语言操作说明。

### 首版不做

- 不把搜索结果称为全网趋势或因果结论；只报告 OpenCLI 实际取得的候选样本和指标。
- 不绕过登录、验证码、风控或平台访问限制；登录失效需提示人工恢复。
- 不自动点赞、关注、评论、发布或删除内容。
- 不在数据库中保存 Cookie、密码或未经用户设置的个人敏感数据。
- 不默认提供多租户、组织权限、复杂 BI 或高可用集群。

## 3. 现有能力与必须先验证的风险

### OpenCLI 能力差异

- 小红书 `xiaohongshu search` 在已安装的 1.8.8 CLI 中支持 `--sort most-liked`、笔记类型、发布时间、搜索范围和位置等筛选；`xiaohongshu note` 可返回正文、标签、点赞/收藏/评论数。
- 抖音 `douyin search` 当前支持关键词和 `--limit`，输出描述、作者、链接、播放/点赞/评论/分享等列；搜索帮助中没有排序参数。首版只能将其排序定义为“当前搜索返回样本内的本地排序”，除非后续确认可用的站内排序命令。
- 两个平台需要已登录的浏览器环境。每次启动前调用 `opencli doctor`，并动态发现 `opencli list -f json` 和站点 `--help`，不可假定不同机器的适配器完全相同。
- 小红书筛选面板是动态 UI。用户操作验证表明悬停“筛选”后再点选项可展开/保留菜单；OpenCLI 1.8.8 的命令式筛选也有上游面板识别问题报告。因此实现必须验证筛选项确已选中、结果有刷新，失败要显式标记，不能默默返回综合排序结果。
- “对标账号作品详情”能力要单独做平台验收：抖音关键词搜索字段与 `user-videos` 字段不同；创作者统计命令是否能读取任意公开账号、是否只对登录账号可用，不能在未验证前承诺。

### 数据解释原则

- 按站内“最多点赞”检索与对候选结果本地排序是两种不同语义，报告中需写明实际使用方式。
- 抖音播放量、小红书收藏量等字段不能直接跨平台横向相加。首版先展示原始指标和各平台内排序；加权热度公式需透明、可配置并经过试跑校准。
- 单轮数据只能支持“本轮高互动候选”；至少两次有时间间隔的快照才可计算增长量/增速。
- LLM 不能补写缺失数据；每个事实性发现需附作品链接或记录 ID，推断与原始事实分开呈现。

## 4. 总体架构

```text
Web UI ───────┐
Agent / MCP ──┼──> FastAPI 应用与统一用例层 ──> SQLite（配置/运行/作品/快照/报告）
Scheduler ────┘               │
                              ├──> Runner / Worker
                              │      ├──> OpenCLI 子进程（JSON 输出）
                              │      ├──> 字段规范化、去重、指标快照
                              │      └──> LLM Provider（结构化分析）
                              └──> Markdown / HTML 报告

Runner 与 OpenCLI、Chrome、Browser Bridge 及登录配置处于同一台机器/用户环境。
```

### 推荐首版技术组合

- **后端**：Python + FastAPI；集中实现配置校验、采集编排、持久化、评分、报告和调度服务。
- **Web UI**：首版用 Jinja2 + HTMX（或同等轻量方案）完成表格、表单、状态刷新；需要更复杂交互时再拆成独立前端。
- **存储**：SQLite + SQLAlchemy/Alembic；本地单实例足够，数据目录通过环境变量配置并做备份说明。
- **调度/后台任务**：独立 Scheduler/Worker 进程，持久化计划和运行状态；首版仅允许一个调度器实例、禁止同一配置重叠执行。正式采用的 APScheduler 版本及持久化 Store 需锁定后验证。
- **Agent 接入**：官方 MCP Python SDK。桌面 Agent 使用本地 `stdio`；需要远程 Agent 时使用 Streamable HTTP，并启用认证；不使用已被取代的旧 SSE 方案。
- **OpenCLI 调用**：封装 `OpenCLIClient`，使用配置项 `OPENCLI_BIN` 指定可执行文件，调用时明确 `-f json`，超时、退出码、stderr、版本和输出结构均进入运行日志。Windows 默认 `opencli` 可能被 WindowsApps 中的旧 OpenCLI App shim 抢先解析，不能只依赖 PATH 名称。
- **LLM**：定义 provider 接口，支持 OpenAI-compatible API；模型、API Base、超时、最大候选数和密钥来自环境变量/本地密钥管理，不写入普通监控配置。

## 6. 数据模型

| 表/实体 | 关键字段与用途 |
|---|---|
| `monitor_configs` | 名称、启停状态、关键词、平台集合、账号集合、筛选 JSON、每词上限、时间范围、LLM 设置引用 |
| `tracked_accounts` | 平台、主页 URL、平台账号 ID、显示名、启停状态 |
| `schedules` | 配置 ID、Cron/间隔、时区、下次运行时间、启停状态、重叠策略 |
| `runs` | 触发来源（手动/定时/Agent）、配置快照、状态、时间、统计、错误摘要、CLI 版本 |
| `content_items` | 平台 + 作品 ID 唯一键、作者、正文/描述、标签、URL、发布时间、首次/最近发现时间 |
| `metric_snapshots` | 作品 ID、采集时间、原始互动字段、平台原始 JSON 引用；保留历史变化 |
| `analysis_reports` | Run ID、模型/provider、prompt 版本、结构化结果、Markdown、创建时间 |
| `run_events` | 步骤状态、重试、警告与诊断；避免把密钥或 Cookie 写入日志 |

原始响应可压缩存储或保存为按 Run 分区的 JSONL 文件；数据库保存引用、解析状态与可查询字段。首版不保存媒体二进制，保留平台链接和可选缩略图 URL。

## 7. 一次运行的处理流程

1. **读取并冻结配置**：把当次关键词、账号、过滤和上限复制到 Run，确保历史报告可复现。
2. **前置检查**：解析 `OPENCLI_BIN`；检查版本和命令能力；运行/读取 `opencli doctor`；确认目标平台登录态可用。前置失败则停止，不产生误导报告。
3. **关键词采集**：每个关键词、每个平台按平台能力表构造搜索命令；XHS 可请求站内排序/筛选，抖音按可用字段获取样本并注明排序口径。
4. **详情补齐**：仅对配置上限内的候选调用详情/账号作品命令，控制请求数量和间隔；单条详情失败不丢弃整个 Run。
5. **规范化/去重**：保留原始值，同时解析数字单位；作品用平台 + ID 合并，指标每次追加快照，不覆盖历史。
6. **排序与指标**：报告原始点赞/评论/收藏/分享/播放量；热度分数按平台独立计算。未来跨日变化用快照差值，不把播放量缺失视为 0。
7. **LLM 分析**：输入经过筛选的内容和明确字段；要求结构化 JSON 输出，包含证据记录 ID；对输出做 schema 校验，失败时仍能生成确定性的基础报告。
8. **报告与通知**：生成 Markdown/HTML，保存在数据库并可导出；可选接入飞书/邮件通知，但不作为首版依赖。
9. **结束与审计**：记录每个平台的部分成功/失败、采集时间、CLI 版本和筛选口径；提供重试单个平台/关键词的入口。

## 8. Web UI 页面

1. **总览**：最近运行状态、候选总数、异常/失败任务、热门关键词和近期变化。
2. **监控配置**：关键词、平台、筛选值、每次条数、账号名单、执行范围；筛选控件按平台展示，允许跨组多选，并提供“重置本平台筛选”；提供“试跑”与保存。
3. **账号库**：账号主页解析、平台身份、启停、最近采集状态。
4. **任务计划**：创建/暂停/恢复/删除；展示时区、下次执行、最近结果；新计划默认先预览，不自动启用。
5. **运行历史**：按配置、平台、日期和状态过滤，展示每步耗时、部分错误和采集记录。
6. **作品与报告**：平台原始互动数、历史变化、标签、正文、来源链接、AI 结论和证据引用。
7. **设置/诊断**：OpenCLI 路径与版本、doctor 状态、浏览器 Profile、LLM 配置状态；已存密钥只显示是否配置，不提供读取或回显。

## 9. MCP 工具设计

工具只做明确、可验证的业务动作，不暴露任意 Shell 执行：

- `list_monitor_configs`：列出可用配置与状态。
- `set_monitor_filters` / `reset_monitor_filters`：按平台设置多项筛选或恢复该配置的平台默认筛选；返回标准化后的最终条件，并在运行时验证是否生效。
- `run_monitor`：按已保存配置触发一次运行，返回 `run_id`；支持 `dry_run` 预览命令。
- `get_run_status`：查询进度、成功/失败计数及错误摘要。
- `get_report` / `list_results`：取报告或指定平台/关键词的结果。
- `create_schedule` / `update_schedule` / `pause_schedule`：创建和管理定时任务，必须给出配置、时区、频率和并发策略；先校验/预览，再由用户明确确认启用。
- `export_report`：导出 Markdown/JSON。

本地优先使用 MCP `stdio`，避免开放监听端口；远程部署使用带认证的 Streamable HTTP。Codex Skill 负责把自然语言意图映射成以上安全工具，不自行拼接任意命令。

## 10. 可移植与开箱即用策略

首版采取 **Native Local Runner**，不承诺“仅用 Docker 就能采集”。OpenCLI 依赖用户配置的 Chrome/扩展/登录态，Runner 必须能访问同一浏览器桥接环境。

交付以下启动体验：

- `setup.ps1` / `setup.sh`：检查 Python/Node/OpenCLI，创建虚拟环境，安装锁定依赖，生成 `.env.example` 的本地副本。
- `doctor` 子命令：输出逐项检查和修复建议；检查具体命令而不只检查 OpenCLI 是否可执行。
- `run` 子命令：无需启动 Web UI 即可由 Agent/脚本执行已保存配置。
- `filters set/reset` 子命令：可批量设置指定配置的平台筛选项，或显式恢复默认；其结果与 Web UI/MCP 共用同一校验服务。
- `web` 子命令：一条命令启动 UI、API 和本地 scheduler/worker。
- `mcp` 子命令：生成/启动 MCP server；提供 Codex 等 Agent 的配置片段。
- JSON/YAML 配置导入/导出：移植规则、关键词和账号清单，排除密钥与浏览器状态。
- `OPENCLI_BIN`：允许配置 npm CLI 的绝对路径，避免 WindowsApps shim 抢先执行旧版；启动诊断明确显示最终解析的可执行文件。
- 部署拓展：若 Web UI 放在远程服务器，另部署一个与 Chrome/OpenCLI 同机的 Runner，通过带认证的队列/API 拉任务并回传结果；不要把已登录 Chrome Profile 复制进容器或仓库。

## 11. 实施里程碑

### 阶段 0：能力验证与产品口径

- 记录 OpenCLI 版本、profile、doctor 状态与平台命令 schema。
- 设计 XHS/Douyin 对照样本，验证关键词、最多点赞排序、筛选项、详情、标签、每类互动字段和账号作品读取。
- 确定“站内排序 vs 本地排序”、缺失值、运行频率、每次上限和 LLM 数据范围。
- 产出字段映射表与 fixture；不能稳定取得的数据标注为后续能力，不预先承诺。

### 阶段 1：核心数据与一次性采集

- 建数据库模型、迁移、配置校验和 JSON 导入/导出。
- 写 OpenCLI 子进程封装、命令能力探测、超时/退出码/错误分类和 mock fixture 测试。
- 实现一次 Run、规范化、去重、指标快照和 Markdown 基础报告；先用 CLI/配置文件验收。

### 阶段 2：Web UI 与人工触发

- 实现配置、账号、手动运行、进度、运行历史、结果和报告页面。
- 加入 Run 锁、局部失败展示、可重试步骤和一键导出。

### 阶段 3：热度分析与 LLM

- 先做确定性的指标排序和标签/关键词统计。
- 加 provider 抽象、结构化提示词、JSON schema、证据引用、成本/条数上限和无 LLM 降级报告。
- 基于真实试跑校准平台内分数；暂不比较跨平台绝对“热度”。

### 阶段 4：定时任务与 Agent/MCP

- 加持久化 scheduler/worker，验证重启恢复、时区、并发、错过的运行和失败重试策略。
- 实现上述 MCP tools，工具复用同一 use-case 层。
- 编写 Codex Skill 与 MCP 配置样例，验证从自然语言触发手动运行、读取报告和创建计划任务的完整链路。

### 阶段 5：其他环境快速部署

- 完成 Windows/macOS/Linux 前置检查脚本、环境变量模板、配置迁移、备份/恢复和常见登录失效排障。
- 做干净环境演练：从克隆仓库到 `doctor` 通过、UI 配置、Agent 调用、定时任务持久化。
- 根据试跑稳定性决定是否支持远程 Runner、PostgreSQL 和多用户部署。

## 12. 风险与缓解

| 风险 | 缓解方式 |
|---|---|
| 站点 UI/搜索排序改版 | 依赖 OpenCLI 官方适配器；启动时检查能力；筛选后验证 active/结果，不满足就失败或显式标记降级；保留可复现 fixture。 |
| 登录过期、验证码、风控 | doctor/登录检查；暂停该平台而非无限重试；要求人工登录，不绕过验证。 |
| 平台指标名称与量纲不同 | 保存原始字段 + 平台映射；分平台展示/评分；缺失不补 0。 |
| 定时任务与浏览器互相争用 | 一个浏览器 Runner 串行执行；任务可配置并发策略；超时释放资源。 |
| LLM 幻觉或过度推断 | 结构化输出、证据 ID、来源链接、schema 校验；报告区分事实与分析。 |
| 内容发送到外部模型 | provider 可配置；限定候选条数；敏感信息最小化；明确数据发送设置。 |
| Windows PATH 解析到错误 OpenCLI | 支持 `OPENCLI_BIN` 绝对路径；doctor 同时展示 PATH 命中顺序和版本。 |
| 计划任务不持久或重复执行 | 持久 Store、唯一任务 ID、运行锁、幂等写入与重启恢复测试。 |

## 13. 首个垂直切片建议

先完成 **“一个关键词 + 小红书 + 最多点赞排序 + 前 5 篇 + 正文/标签/互动 + 数据库快照 + 静态 Markdown 报告”**，不先做抖音、账号名单、Web UI、MCP 或 scheduler。该切片能最早验证从 OpenCLI 到可追溯分析的完整数据链路；之后再把平台连接器抽象出来，逐步加入抖音和其他入口。
